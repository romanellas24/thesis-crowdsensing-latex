\chapter{Smart contract implementation}\label{ch:implementation}
In the previous chapter the protocol was explained, some issues are identified, and mitigation strategies are proposed for the most critical ones.
This chapter describes how the entire protocol is implemented.
The development environment is made of Solidity on Ethereum~\cite{ethereum} and Hardhat as the development and testing framework.
In addition, the chapter also describes how \texttt{PrivacyFirstContract} and its extension, \texttt{PrivacySecondContract} interacts and which functions are overridden and the motivation behind every choice.

\section{Architecture}\label{sec:implementation-architecture}
The architecture is divided between on-chain operations and off chain ones, this distinction exists
because a lot of actions are not executable on the blockchain, like IPFS upload/download and ciphers
usage are not permitted on smart contacts due to the non-deterministic nature of operations such as encryption~\cite{wood2014ethereum}.
The off-chain operations are encapsulated in a SDK that allows actors to interact with the protocol without dealing directly with blockchain primitives.
The structure is composed by two contracts: the base protocol inspired to~\cite{bedogni2024crowdsensing} and another one that extends the base protocol with the mechanisms proposed in Section~\ref{sec:addressing-issues}.

\subsection{Contract hierarchy}\label{subsec:implementation-contract-hierarchy}
The \texttt{PrivacySecondContract} extends \texttt{PrivacyFirstContract}, reusing its core logic without modification.
The functionalities not covered by Section~\ref{sec:addressing-issues}, such as sender enrollment, bond system, majority consensus, and lifecycle are inherited without modification.

There are four \texttt{internal} functions that have been overridden in the \texttt{PrivacySecondContract} to adapt them to the contract needs.

Since the extended contract needs to delivery verification bundles, to prevent duplicate delivery, a \texttt{\_bundleDelivered} mapping is introduced.
For this reason, once the bundle is sent the function \texttt{\_emitVerifierElected} is overridden in \texttt{PrivacySecondContract} to reset the delivery state, allowing a new bundle to be delivered if the verifier slot is reassigned.
This allows the usage of the same location of memory, the delivery of verification bundles is required in order to address the issue of verifiers trust, described in Section~\ref{subsec:addressing-issues-trusted-verifier-issue}.

Since in the Section~\ref{subsec:addressing-issues-geographical-incentive-issue} is described a mechanism to incentive data sensing in heterogeneous geographical areas, it is necessary to change the rewarding system.
For this reason, the method \texttt{\_rewardSender} is overridden and the only modification made is change the calculation of total payout.
In the first version of the contract, the reward is always the full base payout, in the novel one, the contract reads the pre-computed reward from storage.
The effective payout is calculated at the CID publish time, the contract execute the calculus in the \texttt{\_computeDecayedReward} function.
That function executes $k$ times the sqrt of a value (as shown in equation~\ref{eq:proto-design-reward-determination}), in \textit{O(log n)} time using the babylonian method~\cite{kosheleva2009babylonian}, to execute this operation, all values are scaled by a factor of \texttt{1E18} since the EVM, as noted in Section~\ref{sec:chunking-system}, is unable to execute floating point calculus.

The problem of missing verifiers penalties, in addition to bond loss, is discussed in Section~\ref{subsec:addressing-issues-missing-verifier-penalties}.
To address this issue, is required to modify how the smart contract collects the verifiers responses.
For this reason, the functions \texttt{\_rewardCorrectVerifiers} and \texttt{\_tryRewardVerifier} are modified and the responses are saved in mappings that keeps the count of correct votes and wrong ones.
These mappings are required to enforce the kick of systematically wrong voters, as proposed in Section~\ref{subsec:addressing-issues-missing-verifier-penalties}.

The \texttt{PrivacySecondContract} overrides also public functions; the function used to publish decryption key (\texttt{publishVerifierDecryptionKey}) in the \texttt{PrivacyFirstContract} publishes the decryption key through the VerifierEnrolled event, using a key shared among all enrolled verifiers.
In the novel contract, the function is overridden and publish the same event without the key, because, in order to avoid a single decryption key shared among all the verifiers, like described in~\ref{subsec:addressing-issues-trusted-verifier-issue}.
For these reasons, the function \texttt{publishIpfsCid}, is overridden and instead of adding the data in the pending data structure, the data entry requires that \texttt{B} to generate a per-data key pair ($KD_{enc}$, $KD_{dec}$), after which, \texttt{B} calls \texttt{notifyVerificationKeyReady} and the smart contract adds the data to pending data structure.
The novel event \texttt{VerifierElectedForData} notifies \texttt{B} that a verifier has been elected, upon which \texttt{B} delivers a verification bundle via \texttt{deliverVerificationBundle}.
Then a \texttt{VerifierVerificationBundleReady} is emitted and the verifier can finally calculate and submit the verification result using \texttt{submitVerifyResult} overridden function that checks the verification bundle delivery.

In addition, two new functions are introduced: \texttt{getExpectedSenderReward} and \texttt{kickVerifier}, the first one is informative and useful for users to understand which payout they will receive if they send data for a specific chunk in that moment.
The second one can be used from by campaign initiator \texttt{B} to exclude a verifier from the crowdsensing campaign.
In this case the verifier's bond is returned, as the exclusion from the campaign already constitutes a sufficient penalty, consistently with the design choice described in Section~\ref{subsec:addressing-issues-missing-verifier-penalties}.

\subsection{SDK layer}\label{subsec:implementation-sdk-layer}
The SDK layer is responsible for all off-chain operations that the smart contracts cannot or should not perform.
All the cryptographic operations cannot be executed on-chain because the smart contracts are deterministic, so, in the blockchain environment can exist an encryption scheme that is deterministic, because EVM is deterministic~\cite{wood2014ethereum}, so:
\begin{equation}
    \texttt{ENC}_k(m) = c = \texttt{ENC}_k(m). \quad \forall m
    \label{eq:encryption-sceheme-deterministic-formula}
\end{equation}
The equation~\ref{eq:encryption-sceheme-deterministic-formula} shows that given the same message $m$, the same ciphertext  $c$ is always produced.
Deterministic encryption scheme has been shown to be insecure~\cite{katz2020introduction} because if a sender wants to send to a specific receiver the same message two times an adversary $\mathcal{A}$ can understand that the message $m$ was submitted twice because they have seen $c$ flow two times on the network.
Secure schemes such as RSA-OAEP and AES-GCM require a fresh random value per invocation~\cite{rfc8017, nist-sp-800-38d}; the EVM, having no trusted randomness source, cannot provide this.
In addition, all the data sent to the smart contract, including the function call arguments, are visible and stored in the blockchain, so, if in a certain use-case is acceptable that $\texttt{ENC}_k$ is deterministic and the encryption were performed within the smart contract, the content of $m$ is in any case stored and visible over the blockchain.
Furthermore, performing cryptographic operations off-chain avoids the gas overhead that on-chain execution would introduce.

For this reason the SDK must be executed by the protocol actors.
In addition, the proposed SDK exposes an interface that makes it easy for users to parrfc8017ticipate in the campaign and guarantees the correct execution of operations.

In the protocol there are, as before, three types of actors, described in Section~\ref{sec:actors}.
In the SDK architecture, there are three classes, once for each type of Actor.

The campaign initiator \texttt{B} can use two classes, \texttt{OwnerPrivacyFirst} and \texttt{OwnerPrivacySecond}, respectively for the first and the second version of the protocol.
Through the \lstinline{OwnerPrivacyFirst.setup} method, \texttt{B} can deposit the initial token supply and register all the listeners using \lstinline{OwnerPrivacyFirst.startListening}.
For the \texttt{OwnerPrivacySecond} contract, the method \lstinline{startListening} is overridden enabling the registration of listeners for the new events.
With event listeners \texttt{B} is able to handle enrollments automatically.

The sender \texttt{S} can use two classes, \texttt{SenderPrivacyFirst} and \texttt{SenderPrivacySecond}.
The \lstinline{SenderPrivacyFirst.setup} method allows \texttt{S} to enroll to the campaign and pay bond automatically, in addition, the method \lstinline{SenderPrivacyFirst.publishData} automatically handles the encryption and publishes the ciphered CID.
The \texttt{SenderPrivacySecond} was introduced only to pass the correct type to the parametric variable \texttt{C}.
Since Hardhat generates contract types from the ABI rather than from a shared base class, \texttt{SenderPrivacySecond} does not extend \texttt{SenderPrivacyFirst}; however, TypeScript's structural typing allows it to satisfy the type parameter \texttt{C}, as both classes expose the same sender-facing interface.

The verifier \texttt{V} can use two classes, \texttt{VerifierPrivacyFirst} and \texttt{VerifierPrivacySecond}.
The \lstinline{VerifierPrivacyFirst.setup} method allows the verifier to enroll to the campaign and automatically handle the exchange of $K_{\text{dec}}$ and pay bond.
The novel class \texttt{VerifierPrivacySecond} overrides the \lstinline{enroll} method, called by \lstinline{setup}, and also overrides the \lstinline{requestAuthToVerify} to listen for the new event \texttt{VerifierElectedForData}.

\subsection{Off-chain cryptographic utility}\label{subsec:implementation-offchain-encryptions}
The cryptographic utility follows a hybrid scheme: each CID is encrypted with a freshly generated symmetric key, and that key is in turn encrypted under the recipient's public key.
Only the encrypted CIDs travel on the blockchain and the auxiliary public channel.

The symmetric layer uses \texttt{AES-256-GCM}, a NIST-recommended authenticated encryption scheme~\cite{nist-sp-800-38d} that provides both confidentiality (via AES in CTR mode) and integrity/authenticity (via the GHASH authentication tag) in a single pass.
A new symmetric key is sampled at every interaction, so compromise of one session does not affect any other.

The symmetric key is then wrapped with \texttt{RSA-OAEP}, the standard padding scheme for RSA encryption defined in PKCS\#1~v2.2~\cite{rfc8017}.
Its predecessor, PKCS\#1~v1.5, is vulnerable to chosen-ciphertext attacks, which OAEP addresses by introducing randomized padding.

Finally, the proposed SDK demonstrates that the protocol is fully implementable by each actor.
This is not a production-ready library but a reference implementation; as such, the keys live in the program's memory, for this reason, keys are not protected by a hardware security module.

\subsection{Initialization and deployment}\label{subsec:implementation-protocol-init}
The campaign initiator \texttt{B} generates their own key pair $(PK_B, SK_B)$ using the \texttt{cipher} in the SDK.

    label={lst:proto-implementation-pfc-owner-sender-enrollment}]
handleSenderEnrollment(senderAddress: string, encryptedPubKeyJson: string) {
  const bundle = JSON.parse(encryptedPubKeyJson);
  const senderPubKey = cipher.decryptStringHybrid(keys.privateKey, bundle);
  const encryptedKenc = JSON.stringify(
    cipher.encryptStringHybrid(senderPubKey, encryptionKeys.encryptionKey));
  contract.publishSenderEncryptionKey(
    senderAddress, encryptedKenc);
}
\end{lstlisting}

The \lstinline{publishSenderEncryptionKey} call completes the registration and creates a struct to store the sender's information.

The handler is quite simple, since the \lstinline{SenderEncryptionKeyReady} has two parameters (senderAddress, encryptionKeyCiphertext), if \texttt{S} sees their address in senderAddress the handler is triggered and removed.
The ciphertext of $K_{enc}$ is returned; the sender then uses $SK_S$ to decrypt and obtain $K_{enc}$.

With this implementation the sender enrollment reflects the design choices made in Section~\ref{subsec:proto-sender-enrollment}.

\subsection{Verifier enrollment}\label{subsec:implementation-verifier-enrollment}
This Section describes the verifier enrollment phase for the \texttt{PrivacyFirstContract}.
The extended protocol version is discussed in Sections~\ref{subsec:extended-protocol-extended-verifier-enrollment} and~\ref{subsec:extended-protocol-extended-data-submission} which implement the modifications in Section~\ref{subsec:addressing-issues-trusted-verifier-issue}.

In the \texttt{PrivacyFirstContract} the implementation is very similar to the one realized for senders, shown in Section~\ref{subsec:implementation-sender-enrollment}.

The verifiers can use the \texttt{VerifierPrivacyFirst} (\texttt{VPF}) class to join the crowdsensing campaign.
The constructor of the class automatically generates $(PK_V, SK_V)$ key pair and require the verifyCallback to execute on every data to check.

After the object initialization, the verifier has to call the \lstinline{setup} method.
The method calls the \lstinline{enroll} method and \lstinline{payBond}, which handles the bond payment, like the one implemented for the senders.
The workflow is the same for senders but with different functions to invoke and event to wait for.

The general workflow is the following:
\begin{enumerate}
    \item \texttt{V} register a listener for the \lstinline{VerifierDecryptionKeyReady} event;
    \item \texttt{V} retrieve $PK_B$ which is embedded in the smart contract;
    \item \texttt{V} encrypt $PK_V$ using $PK_B$ and sends it to the smart contract using the \lstinline{publishEncryptedVerifierPublicKey} function;
    \item The Smart Contract triggers via \lstinline{VerifierEnrolledEvent} the campaign initiator which is listening for this event as shown in the Listing~\ref{lst:proto-implementation-opf-start-listening};
    \item \texttt{B} via the \lstinline{handleVerifierEnrollment} handler, encrypts $K_{dec}$ using $PK_V$, used for data decryption during verification;
    \item \texttt{B} sends the calculated ciphertext to the smart contract using \lstinline{publishVerifierDecryptionKey} which updates the Smart Contract state and the verifier is officially in the campaign, finally, \lstinline{VerifierDecryptionKeyReady} event is emitted;
    \item \texttt{V} is triggered by the event and get $K_{dec}$
\end{enumerate}

After these steps the verifier can verify data and start the verification workflow, that will be discussed in Section~\ref{subsec:implementation-verification}.

With this implementation the verifier enrollment reflects the design choices made in Section~\ref{subsec:proto-verifier-enrollment}.

\subsection{Data submission}\label{subsec:implementation-data-submission}
The data submission is the core phase where the crowdsensing campaign obtains data.

The SDK implementation for the senders is written in \texttt{SenderPrivacyFirst} (\texttt{SPF}) and is shown in Listing~\ref{lst:proto-implementation-spf-sender-publish-data}.
\begin{lstlisting}[
language=typescript,
caption={Sender \lstinline{publishData} method to send data to the campaign},
label={lst:proto-implementation-spf-sender-publish-data}]
async publishData(plainCid: string, position: any) {
if (!this.kenc) throw new Error("Not enrolled - Kenc not available");

const encrypted = this.cipher.encryptStringHybrid(this.kenc, plainCid);
const cidBytes = toUtf8Bytes(JSON.stringify(encrypted));
return this.contract.connect(this.signer).publishIpfsCid(cidBytes, position);
\end{lstlisting}

Basically, the method checks if $K_{enc}$ is available, if not, it throws an error, otherwise, uses $K_{enc}$ to encrypt the CID returned by the IPFS node after uploading the encrypted data, where they have submitted the data and publishes the encrypted CID using the smart contract function \lstinline{publishIpfsCid}.

The function, which is shown in Listing~\ref{lst:proto-implementation-publish-ipfs-cid}, performs a series of checks such as bond availability, maximum data count per chunk and per sender, and geographical area validation.
If any of these checks fails, then the entire transaction is reverted, but if the data is submitted a struct to store submission information is created and the data index is added to the pending queue, waiting for verification.
In this phase of the protocol, no action from the campaign initiator is required; the \lstinline{DataVerificationRequestedEvent} event is emitted to notify verifiers that new data is available for verification.

    language=solidity,
    caption={\lstinline{publishIpfsCid} function implementation},
    label={lst:proto-implementation-publish-ipfs-cid}]

function publishIpfsCid(bytes calldata encryptedCid, GlobalPosition calldata position) external virtual {
  require(_campaignOpen, "Campaign is closed");
  require(_senders[msg.sender], "Only senders allowed...");
  require(position.isValid(), "Invalid Coordinates");
  require(_senderInformation[msg.sender].dataSubmitted
    < _config.needs.maxDataPerSender
    || _config.needs.maxDataPerSender == 0,
  "Max data limit reached");

  // if maxDataPerSender == 0 (unlimited), bond check is skipped
  // since total bond cannot be pre-computed
  require(_senderInformation[msg.sender].bondBalance
    >= _config.rewardConfig.dataSenderBondPerData
    || _config.needs.maxDataPerSender == 0,
    "Insufficient DST balance in bond");

  PackedPosition memory packed = position.packCoordinates();
  (uint16 chunkIndex, bool inside) = _getChunkIndex(packed);
  require(inside, "Outside campaign area");
  require(_dataPerChunkReceived[chunkIndex]
    < _config.needs.maximumDataPerChunk
    || _config.needs.maximumDataPerChunk == 0,
  "Too many data in this chunk!");

  _dataEntries[_dataCount] = DataEntry({
    sender: msg.sender,
    encryptedCid: encryptedCid,
    status: DataStatus.PENDING,
    completedChecks: 0,
    positiveChecks: 0,
    assignedChecks: 0,
    chunkIndex: chunkIndex,
    earliestSlotDeadline: 0});
  _dataPerChunkReceived[chunkIndex]++;
  _senderInformation[msg.sender].dataSubmitted++;
  emit DataVerificationRequestedEvent(_dataCount);

  _addToPending(_dataCount);

  _dataCount++;

  if (_config.needs.maxDataPerSender > 0) {
    unchecked {
      _senderInformation[msg.sender].bondBalance = _senderInformation[msg.sender].bondBalance -
      _config.rewardConfig.dataSenderBondPerData;
    }}
}

The \lstinline{publishIpfsCid} function requires, among others, the \lstinline{position} parameter of type \lstinline{GlobalPosition}, has four fields, two for latitude and two for longitude.
For both coordinates a field is used for the integer part, the second one for the fractional part as up to seven decimal digits.
The struct is shown in Listing~\ref{lst:proto-implementation-globalposition-struct}.
\begin{lstlisting}[
    language=solidity,
    caption={\lstinline{GlobalPosition} implementation struct},
    label={lst:proto-implementation-globalposition-struct}]
struct GlobalPosition {
  int32 latitudeInteger; // [-90, +90]
  int32 latitudeDecimal; // (-10_000_000, +10_000_000) sign used iff integer is 0.
  int32 longitudeInteger;// [-180, +180]
  int32 longitudeDecimal;// (-10_000_000, +10_000_000) sign used iff integer is 0.
}
\end{lstlisting}
The struct comes with a library, called \lstinline{GlobalPositionLibrary}.
The aim of this library is straightforward: make a clear interface to work with the introduced struct.
The library has two functions: \lstinline{isValid} and \lstinline{packCoordinates}.

The \lstinline{isValid} function returns true if the coordinate is valid, false otherwise.
A GlobalPosition is valid when its integer parts stay within the standard geographic ranges, latitude between -90 and +90 inclusive, longitude between -180 and +180 inclusive.
Each decimal part has a magnitude strictly below $10,000,000$, since that's the value of exactly one degree in E7 precision and anything at or above it would overflow into the next integer step.

The sign of the coordinate follows a simple rule: when the integer part is non-zero it carries the sign, and the decimal contributes only its magnitude; when the integer part is zero, the decimal carries the sign instead.
This second branch is what makes the band (-1°, 0°) representable on both axes, without it, every point between the equator and one degree south, or between Greenwich and one degree west, would be unreachable.

The \lstinline{packCoordinates} function collapses the split (integer, decimal) representation into a single signed 32-bit integer per axis, scaled by $10^7$.

The resulting E7 format has about 1.11 cm of precision.

The code is shown in Listings~\ref{lst:proto-implementation-globalposition-library}.
\begin{lstlisting}[
    language=solidity,
    caption={\lstinline{GlobalPositionLibrary} implementation},
    label={lst:proto-implementation-globalposition-library}]
library GlobalPositionLibrary {
  int32 internal constant DEC_BOUND = 10_000_000;

  function isValid(GlobalPosition memory p) internal pure returns (bool) {
    if (p.latitudeInteger < -90
      || p.latitudeInteger > 90) return false;
    if (p.latitudeDecimal <= -DEC_BOUND
      || p.latitudeDecimal >= DEC_BOUND) return false;
    if ((p.latitudeInteger == 90 || p.latitudeInteger == -90)
      && p.latitudeDecimal != 0) return false;
    if (p.longitudeInteger < -180 ||
      p.longitudeInteger > 180) return false;
    if (p.longitudeDecimal <= -DEC_BOUND ||
      p.longitudeDecimal >= DEC_BOUND) return false;
    if ((p.longitudeInteger == 180
      || p.longitudeInteger == -180)
      && p.longitudeDecimal != 0) return false;
    return true;
  }

  function packCoordinates(GlobalPosition memory p) internal pure returns (PackedPosition memory) {
    //valid checks ...
    return PackedPosition({
    latE7: int32(_combine(p.latitudeInteger,
      p.latitudeDecimal)),
    lonE7: int32(_combine(p.longitudeInteger,
      p.longitudeDecimal))
    });
  }

  function _combine(int32 integerPart, int32 decimalPart) private pure returns (int64) {
    int64 base = int64(integerPart) * 10_000_000;
    int64 dec  = int64(decimalPart);
    int64 absDec = dec < 0 ? -dec : dec;
    if (integerPart > 0) return base + absDec;
    if (integerPart < 0) return base - absDec;
    return dec;
  }
}
\end{lstlisting}

function _getChunkIndex(PackedPosition memory packed) internal view returns (uint16, bool) {
  // Check bounds
  if (packed.latE7 < _smartContractOrigin.latE7 ||
    packed.latE7 >= _smartContractEnd.latE7) return (0, false);
  if (packed.lonE7 < _smartContractOrigin.lonE7 ||
    packed.lonE7 >= _smartContractEnd.lonE7) return (0, false);

  // Calculating row and col
  int32 chunkSize = int32(uint32(_config.chunkConfig.chunkSize));
  uint16 row = uint16(uint32((packed.latE7 - _smartContractOrigin.latE7) / chunkSize));
  uint16 col = uint16(uint32((packed.lonE7 - _smartContractOrigin.lonE7) / chunkSize));

  uint16 index = row * _config.chunkConfig.chunk4Side + col;
  return (index, true);
}

\subsection{Verification workflow}\label{subsec:implementation-verification}
Verifiers have listeners on the \lstinline{DataVerificationRequestedEvent} event and they are waiting for it.
As shown in Section~\ref{subsec:implementation-data-submission}, at the end of the encrypted CID publishing the smart contract emits the \lstinline{DataVerificationRequestedEvent}.
This event is emitted in this phase only by the \texttt{PrivacyFirstContract}, not in the extended one.
Although \lstinline{DataVerificationRequestedEvent} has a parameter that indicates the dataId, this parameter is ignored, because the smart contract selects which data to verify in order to enforce a cooldown mechanism.

The \texttt{VerifierPrivacyFirst} (\texttt{VPF}) exposes the method \lstinline{requestAndVerify} that allows the verifier to join the verification process of data, the same name is used to describe a function in the smart contract that validates and checks the verifier's requests.
At the end of the validation performed by the smart contract, the \lstinline{VerifierElected} event is emitted and the verifier can proceed with validity checks.
The SDK \lstinline{requestAuthToVerify} method calls the smart contract function and returns the \lstinline{decryptedCid}, after which the verifier can execute checks.
The smart contract \lstinline{requestAuthToVerify} function is shown in Listing~\ref{lst:proto-implementation-pfc-request-auth-to-verify}.

\begin{lstlisting}[
    language=solidity,
    caption={\lstinline{requestAuthToVerify} function implementation},
    label={lst:proto-implementation-pfc-request-auth-to-verify}]
function requestAuthToVerify() external {
  //Checks on enrollment and bond

  for (uint256 i = 0; i < _pendingDataIds.length; i++) {
    uint256 dataIndex = _pendingDataIds[i];

    //cooldown check
    if (_verifierInformation[msg.sender].hasVerified) {
      uint256 last = _verifierInformation[msg.sender].lastVerified;
      if (dataIndex >= last &&
        dataIndex < last + _config.needs.verifierCooldown) continue;
    }

    //checks on data slots
    if (_dataEntries[dataIndex].assignedChecks
      >= _config.needs.checksRequired
      && _dataEntries[dataIndex].earliestSlotDeadline
      > block.timestamp) {continue;}

    (uint8 slotIndex, bool found) = _findAvailableSlot(dataIndex);
    if (!found) continue;

    //Underflow safety. Bond decreasing
    unchecked {
        _verifierInformation[msg.sender].bondBalance =
          _verifierInformation[msg.sender].bondBalance
          - _config.rewardConfig.dataVerifierBondPerData;
    }

    uint48 deadline = uint48(block.timestamp + _config.needs.verificationTimeout);

    _verificationSlots[dataIndex][slotIndex] = VerificationSlot({
      verifier: msg.sender,
      result: false,
      completed: false,
      deadline: deadline});

    // Update earliestSlotDeadline if unset or if the new deadline is sooner
    if (_dataEntries[dataIndex].earliestSlotDeadline == 0 ||
      deadline <
      _dataEntries[dataIndex].earliestSlotDeadline) {
        _dataEntries[dataIndex].earliestSlotDeadline
          = deadline;}

    //Assigning slots
    if (slotIndex >=
      _dataEntries[dataIndex].assignedChecks) {
        _dataEntries[dataIndex].assignedChecks
        = slotIndex + 1;}

    _verifierInformation[msg.sender].verifyingData = dataIndex;
    _verifierInformation[msg.sender].isVerifying = true;

    _emitVerifierElected(msg.sender, dataIndex, slotIndex);
    return;
  }
  revert("No data available for verification");
}
\end{lstlisting}

The function performs multiple checks to guarantee a fast data retrieval with the minimum amount of gas usage as discussed in Section~\ref{sec:implementation-gas-optimization}, the \lstinline{_findAvailableSlot} function checks if a data has a free slot, if not, the function analyzes the next pending entry.
In \lstinline{_emitVerifierElected}, a \lstinline{VerifierElected} event is emitted; the verifiers are waiting for that event, when triggered by the event, they can invoke the \lstinline{verifyCallback} that is given in the constructor, as explained in Section~\ref{subsec:implementation-verifier-enrollment}.
In addition, the verifiers can use \lstinline{submitVerifyResult} function of the smart contract to deliver the verification result.
A summary of verify workflow is shown in \lstinline{requestAndVerify} method of \texttt{VerifyPrivacyFirst} class, whose implementation in shown in Listing~\ref{lst:proto-implementation-vpf-request-and-verify}.
\begin{lstlisting}[
    language=typescript,
    caption={\texttt{VPF}'s \lstinline{requestAndVerify} method implementation},
    label={lst:proto-implementation-vpf-request-and-verify}]
async requestAndVerify(): Promise<{ dataId: number;
    decryptedCid: string;
    result: VerificationResult }> {
    try{
    const {dataId, decryptedCid}
      = await this.requestAuthToVerify();
    const result = this.verifyCallback(decryptedCid, dataId);
    const tx = await this.submitResult(result);
    await tx.wait();
    return {dataId, decryptedCid, result};
  } catch (ignored){}
  return {dataId: -1, decryptedCid: "", result: VerificationResult.CANNOT_COMPLETE};
}
\end{lstlisting}

When the majority of required verifiers votes with the same significant result (data is valid or invalid), the validated data is removed from the pending queue and the smart contract rewards the correct verifiers and the sender, if the data was valid.

uint256[] internal _pendingDataIds;
mapping(uint256 => uint256) internal _pendingIndex;

//Insert into data structure
function _addToPending(uint256 dataId) internal {
    _pendingIndex[dataId] = _pendingDataIds.length;
    _pendingDataIds.push(dataId);
}

//Remove from data structure
function _removeFromPending(uint256 dataId) internal {
    uint256 idx = _pendingIndex[dataId];
    uint256 lastId = _pendingDataIds[_pendingDataIds.length - 1];
    _pendingDataIds[idx] = lastId;
    _pendingIndex[lastId] = idx;
    _pendingDataIds.pop();
    delete _pendingIndex[dataId];
}
