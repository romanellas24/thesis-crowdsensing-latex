\chapter{Protocol design} \label{ch:protocol-design}
In this chapter the protocol design is presented.
The protocol leverages smart contracts and asymmetric encryption to ensure confidentiality and data integrity.
The protocol adopts a multi-layered encryption approach, performed off-chain, and uses the smart contract as a communication channel for the crowdsensing campaign.
The key exchange is made to and from the campaign initiator (referred from now as ''\texttt{B}'').
\texttt{B} uses their private/public key pair for enhancing confidentiality, in this way, only \texttt{B} can access the other actors' public key, namely senders (\texttt{S}) and verifiers (\texttt{V}).
This approach shares similarities with prior work on asymmetric key exchange mediated by smart contracts~\cite{muth2020smartdhx}, although it differs substantially in both application domain and protocol design.

\section{Actors}\label{sec:actors}
The protocol involves several actors that are described in the following subsections.

\subsection{Campaign initiator}\label{subsec:campaign-initiator}
The campaign initiator (\texttt{B}) is the actor interested for collecting data for some reason.
They define the geographic area where the smart contract works and set the smart contract hyperparameters, all configurable parameters are explained in Appendix~\ref{ch:appendix-a-parameters}.
In addition, they deposit the reward funds into the smart contract to ensure that funds are available and senders and verifiers can be compensated.
The details of rewarding model are described in the~\ref{subsec:proto-rewarding-model} subsection.

\subsection{Sender}\label{subsec:sender}
Senders (hereafter referred to as \("\)\texttt{S}\("\)) are the users who contribute to the crowdsensing campaign by submitting data retrieved from the environment where they are located.
To contribute, senders, after the joining phase, upload data to IPFS and submit the encrypted CID through the smart contract.

\subsection{Verifier}\label{subsec:verifiers}
Verifiers (hereafter referred to as \("\)\texttt{V}\("\)) are the users who contribute to the crowdsensing campaign by executing data quality checks and submitting the verification result through smart contract functions.
To contribute, verifiers listen for events emitted by the smart contract.
Upon receiving a \texttt{DataVerificationRequestedEvent}, they request verification authorization; if granted, they execute the verification and publish the result.

\subsection{Smart Contract}\label{subsec:smartcontract}
Smart Contract (hereafter referred to as \("\)\texttt{SC}\("\)) is the actor that mediates the interaction between all other actors.
In addition, this actor handle the payment model and the bond mechanism, described in Sections ~\ref{subsec:proto-rewarding-model} and ~\ref{subsec:proto-bond-model}.
The smart contract acts as the sole communication channel between participants, eliminating direct interaction.
It stores encrypted cryptographic material and data references on-chain, and enforces campaign lifecycle rules such as participation thresholds and automatic closure.


\section{Protocol workflow}\label{sec:proto-workflow}
The protocol workflow is described in the following subsections.
Each phase is illustrated by a corresponding sequence diagram.
The protocol design follows and extends the work presented in~\cite{bedogni2024crowdsensing}.

For clarity, the following notation is adopted throughout this chapter:
\begin{itemize}
    \item $\text{Enc}(m, PK)$: encryption of message $m$ using public key $PK$;
    \item $\text{Dec}(c, SK)$: decryption of ciphertext $c$ using private key $SK$;
    \item $(PK_X, SK_X)$: public and private key pair of actor $X$.
\end{itemize}

\subsection{Initialization}\label{subsec:proto-init}
Initialization phase consists of the following steps.
The campaign initiator (\texttt{B}) deploys the smart contract, indicating all the parameters, described in Appendix~\ref{ch:appendix-a-parameters}.
Before the deployment, \texttt{B} generates its pair of private/public key $(PK_B, SK_B)$ which is used for sender and verifiers enrollment (explained respectively in Section~\ref{subsec:proto-sender-enrollment} and Section~\ref{subsec:proto-verifier-enrollment}) and generates also an asymmetric key pair $(K_{enc}, K_{dec})$.
After the deployment, the owner approves the transfer of a \texttt{totalDst}
quantity of DST (described in~\ref{subsec:data-sent-token}) to the smart contract address,
and then confirms the deposit.

\subsection{Sender enrollment}\label{subsec:proto-sender-enrollment}
Any sender who wants to contribute to the crowdsensing campaign has to generate a private/public key pair. $(PK_S, SK_S)$
Subsequently, \texttt{S} retrieves the public key of \texttt{B} from the smart contract.
Then \texttt{S} computes:
\[
    c^{S}_{1} = \text{Enc}(PK_S, PK_B)
\]
and sends $c^{S}_{1}$ to the smart contract.
Upon receiving the ciphertext, the smart contract emits an event that \texttt{B} monitors.
When \texttt{B} detects the event, it retrieves the sender address and $c^{S}_{1}$from it.

Then \texttt{B} computes:
\[
    PK_S = \text{Dec}(c^{S}_{1}, SK_B)
\]
At this point, \texttt{B} possesses \texttt{S}'s public key and can establish a secure channel. \texttt{B} computes:
\[
    c^{S}_{2} = \text{Enc}(K_{enc}, PK_S)
\]
And sends $c^{S}_{2}$ to the smart contract which triggers an event to notify \texttt{S}.
Finally, \texttt{S} retrieves $c^{S}_{2}$ from the emitted event and computes
\[
    K_{enc} = \text{Dec}(c^{S}_{2}, SK_S)
\]
This key will be used for CID encryption, as shown in Section~\ref{subsec:proto-datasubmit}.

\subsection{Verifier enrollment}\label{subsec:proto-verifier-enrollment}
Verifiers contribute to crowdsensing campaign by performing data quality checks on the data.
Any verifier who wants to contribute to the crowdsensing campaign has to generate a private/public key pair $(PK_V, SK_V)$.
Subsequently, \texttt{V} retrieves the public key of \texttt{B} from the smart contract.
Then \texttt{V} computes:
\[
    c^{V}_{1} = \text{Enc}(PK_V, PK_B)
\]
then sends $c^{V}_{1}$ to the smart contract.

Upon receiving the ciphertext, the smart contract emits an event that \texttt{B} monitors.
When \texttt{B} detects the event, it retrieves the verifier address and $c^{V}_{1}$ from it.

Then \texttt{B} computes:
\[
    PK_V = \text{Dec}(c^{V}_{1}, SK_B)
\]
At this point, \texttt{B} possesses \texttt{V}'s public key and can establish a secure channel. \texttt{B} computes:
\[
    c^{V}_{2} = \text{Enc}(K_{dec}, PK_V)
\]
and sends $c^{V}_{2}$ to the smart contract which triggers an event to notify \texttt{V}.
Finally, \texttt{V} retrieves $c^{V}_{2}$ from the emitted event and computes
\[
    K_{dec} = \text{Dec}(c^{V}_{2}, SK_V)
\]
This key will be used for CID decryption, as shown in Section~\ref{subsec:proto-verification}.

\subsection{Data submission}\label{subsec:proto-datasubmit}
Data submission is the main process of the protocol.
It enables senders to contribute data references to the campaign.
When \texttt{S} has data for the campaign, it encrypts data with $K_{enc}$ key and uploads the encrypted data to IPFS.
IPFS returns a Content Identifier (CID, see Section~\ref{subsec:ipfs})
\[
    CID_{ciphered} = \text{Enc}(\text{CID}, K_{enc})
\]
Then \texttt{S} sends $CID_{ciphered}$ to the smart contract along with the geographic position of the measurement.
Once the data is registered, a specific event is emitted by the smart contract which is monitored by verifiers.
This concludes the data submission phase and triggers the verification phase (described in Section ~\ref{subsec:proto-verification}).

\subsection{Verification}\label{subsec:proto-verification}
The verification phase is performed by verifiers, whose goal is to determine whether a given data entry meets the quality requirements of the campaign.
To mitigate the risk of a single malicious or faulty verifier, each data entry is independently verified through multiple \textit{verification slots}.
The number of slots is configured to be odd, so that a strict majority decision is always reachable and ties are structurally avoided.
Slots are not statically assigned: each verifier must explicitly request authorization, and the smart contract elects it to an available slot only if the eligibility and cooldown constraints are satisfied.

A verifier \texttt{V} can request authorization either upon receiving a \texttt{DataVerificationRequestedEvent} or by polling autonomously.
Please note that the smart contract is not constrained to return the data entry that triggered the event: any pending data entry eligible for verification can be returned.

The authorization request has two possible outcomes:
\begin{itemize}
    \item The \texttt{VerifierElected} event is emitted, carrying among its parameters the ciphered CID and the address of the elected verifier;
    \item The authorization is denied, in which case \texttt{V} must wait before attempting again.
\end{itemize}

When \texttt{V} is elected, it can proceed with the verification.
\texttt{V} computes:
\[
    CID = \text{Dec}(CID_{ciphered}, K_{dec})
\]
\texttt{V} then retrieves the encrypted data from IPFS using the $CID$ and performs quality checks on it.
After the checks, \texttt{V} submits the verification result to the smart contract.

As soon as a strict majority of slots agrees on a result (either positive or negative), the smart contract flags the data entry as \texttt{VALID} or \texttt{INVALID}, and the verification process concludes.
Any remaining unfilled slots are no longer needed and are effectively discarded.
If \texttt{V} cannot complete the task or misses the deadline, it can submit the special result \texttt{CANNOT\_COMPLETE}; in this case, the verification slot is released and becomes available for reassignment.
Once the data entry is flagged, payments and penalties are applied, as described in Section~\ref{sec:incentive-mechanisms}.
